# 对局通过确定性重放从事件日志恢复

对局改在浏览器标签页里运行后，页面关闭或刷新就会中断对局；我们要求对局能从事件日志恢复到停下处继续，而不是记为终止。引擎的状态本就由事件折叠而来，但控制流（处于哪个阶段、对话轮到谁、剩余发言次数）只存在于 `runGame` 这个 async 过程中，因此恢复时从头重新执行 `runGame`：已在日志里的部分不发请求、不写日志，只核对引擎重新产生的事件与日志一致，选手、说书人与手动裁量直接取日志中被采用的结果，随机数用 `game.created` 里的种子重新生成；日志耗尽后切换为实时运行。

## Considered Options

- **把引擎改写为纯状态机**（控制流位置进入状态，`next(state) → effect`）：恢复最直接，但等于重写整个引擎，被否决。
- **恢复不了就记为终止**：最省事，但浪费已花费的模型调用，也违背“暂停可以继续”的语义，被否决。

## Consequences

- 引擎必须保持确定性：除了经由 ports 的输入外，不得读取时间、`Math.random` 等外部状态。
- 并行批次中的决策写入顺序不确定，重放时按座位与请求匹配，而不是按日志位置。
- 引擎行为或事件形状一旦改变，必须提升 `shared/game/version.ts` 中的 `ENGINE_VERSION`；对局配置以 `engineVersion` 记录它，摘要以 `compatible` 表示版本是否相符。版本不符的对局既不能观战也不能继续。版本相同但重放结果与日志不符时，对局以“引擎错误”终止。

## 应用 API 的实时运行

`app/api/index.ts` 导出创建、列表、摘要、按观察者读取与订阅事件、终止、提交手动裁量和决策失败后的继续。订阅先补发起始 seq 之后的投影，再推送新事件，返回取消订阅函数。对局和事件写入 IndexedDB；`app/api/game-runner.ts` 在标签页模块状态中维护各局 runner，跨局共享 `app/api/llm.ts` 的提供商并发队列。引擎仍只通过 `Ports` 访问输入，后续恢复可在调用 `runGame` 前组合重放 ports，不需要改写引擎控制流。页面已全部使用应用 API，不再运行 Nitro API、SSE 或 SQLite；`mise run build` 通过 `nuxt generate` 生成静态文件，`mise run start` 仅在 `127.0.0.1` 提供静态文件（端口由 `PORT` 指定，默认 3000）。提供商凭据直接保存在当前浏览器的 IndexedDB，浏览器直接调用提供商，提供商必须允许该来源的 CORS 请求。本阶段只支持当前 runner 的继续，刷新后的重放恢复另行实现。
